# Технические гарантии и границы

## Хранение и кеш

PostgreSQL содержит отдельные базы catalog, inventory, rental, customers, billing,
maintenance, auth. Для каждой создаётся собственная роль; CONNECT другим ролям
через PUBLIC отозван. Один сервер PostgreSQL используется для удобства локального запуска;
БД могут быть перенесены на отдельные серверы изменением DATABASE_URL.

SQLUnitOfWork берёт transaction-level advisory-lock в своей БД. Проверка правила,
изменение снимка агрегата, увеличение версии кеша и создание события выполняются
в одной транзакции. Другие сервисы не читают эту БД: исключение — диагностические
интеграционные тесты, которые проверяют физическую запись данных.

Redis хранит JSON по ключу `<service>:<kind>:<revision>:<id|all>` с TTL 60 секунд.
Текущая revision читается из PostgreSQL. После commit новой версии старый ключ больше
не используется, даже если Redis был недоступен во время записи. После первого save
репозиторий не кеширует данные текущей транзакции, чтобы rollback не оставил грязные данные.
Это уменьшает чтение снимков и сериализацию, но не устраняет все SQL-запросы: версия
всё ещё проверяется в БД. Auth не кеширует хеши паролей.

SQLite оставлен для быстрых компонентных тестов; рабочий Compose использует PostgreSQL.
Репозиторий SQLAlchemy и UnitOfWork реализуют порты application каждого сервиса.

## Outbox/inbox

`outbox`: UUID, envelope, created_at, published. Запись создаётся вместе с бизнес-изменением.
Worker публикует persistent message в durable exchange `rental.events`, требует publisher
confirm и mandatory routing, затем помечает запись опубликованной. Сбой после отправки
и до commit приводит к повторной доставке. Неотправленная запись остаётся в outbox.

Очереди `rental.events`, `inventory.events`, `billing.events` создаются до публикаций.
Consumer выполняет один локальный UnitOfWork: проверка inbox → обработчик → новые outbox
события → запись inbox → commit. Только затем отправляется ACK. Сбой до commit приводит
к rollback и повтору сообщения. Семантические повторы дополнительно ограничены состоянием
saga, владельцем резерва и reference платежа.

Повреждённые или неизвестные сообщения направляются в `<service>.dead` через DLX
`rental.dead`. Временные исключения обрабатываются NACK/requeue с задержкой;
соединение восстанавливается после ошибки. Inbox/outbox не удаляются автоматически,
чтобы сохранить историю в учебном проекте. Для эксплуатации нужны политика очистки,
мониторинг, ограничение повторов и операционный процесс работы с DLQ.

Оба вида подтверждений описаны в [документации RabbitMQ](https://www.rabbitmq.com/docs/confirms).

## Saga

Оркестратор находится в rental, состояние хранится в Checkout и переживает перезапуск.
Каждый участник совершает локальную транзакцию. Инвентарь в reserved блокируется от
ручных изменений до решения процесса. При отказе оплаты компенсация освобождает резерв,
а rental после подтверждения отменяет бронирование. Деньги списываются только учебным
симулятором; внешних необратимых действий обработчик не выполняет.

Промежуточные состояния доступны по GET /api/v1/checkouts/{id}. Бронирование со статусом
checkout_pending продолжает занимать временной интервал. Создание договора происходит
только после inventory.issued. Закрытие такого договора отправляет inventory.return;
возврат физического состояния становится виден асинхронно.

## gRPC и авторизация

Контракт protobuf хранится в `packages/runtime/src/rental_runtime/proto/customers.proto`.
Rental через порт CustomerGateway получает признак существования и доступности клиента.
Дедлайн вызова — 2 секунды. Сервер проверяет INTERNAL_RPC_TOKEN. Ошибка транспорта
преобразуется в HTTP 503; блокировка клиента — 409; отсутствие — 404. Домен не импортирует gRPC.
Проверка относится к моменту бронирования; это не распределённая блокировка клиента.
Основа генерации: [документация gRPC Python](https://grpc.io/docs/languages/python/basics/).

Auth хранит Argon2-хеши и подписывает RS256 JWT. Остальные сервисы проверяют подпись,
фиксированные issuer/audience, exp и обязательные claims, затем роль. Закрытого ключа
в остальных сервисах нет. Публичная регистрация не принимает роль из запроса.
Назначение ролей защищено require_admin. Токены не сохраняются в Redis или в логах.

## CI

Unit/component job не требует Docker. Integration job использует отдельный dind,
строит тот же Compose-стенд и запускает тестовый контейнер. Для совместимости с удалённым
daemon ephemeral JWT-ключи доставляются через docker cp в изолированные volumes;
JUnit копируется обратно после завершения. Образы не содержат ключей или .env.
Runner должен разрешать privileged dind: [GitLab services](https://docs.gitlab.com/ci/services/).
